# Agent Runtime Design v0.1 Linux-Only

## 1. Summary

This project is a Linux-only, Rust-based distributed agent runtime.

The goal is to let coding agents such as Codex, Claude Code, OpenCode, or a human CLI control multiple Linux machines through a coordinator-worker architecture.

The first target is multi-node GPU training, but the runtime should remain general enough to support:

- multi-machine command execution
- distributed training launch
- distributed evaluation
- benchmark orchestration
- log collection
- artifact collection
- future sandboxed agent execution

Core principle:

> Agents should not directly own remote shells.  
> Agents should call a coordinator.  
> The coordinator sends typed operations to workers.  
> Workers enforce local policy and sandbox boundaries before executing anything.

In the first version, the system may run in:

```text
policy = allow_all
sandbox = none
````

But the code path must already include:

```text
PolicyEngine -> SandboxBackend -> Executor
```

So later sandbox and permission support can be added without rewriting the system.

---

## 2. Goals

### Functional goals

1. Run a worker daemon on each Linux machine.
2. Let workers connect to a central coordinator.
3. Let the coordinator launch, monitor, and stop jobs across workers.
4. Support long-running processes and streaming logs.
5. Support multi-node training launchers such as:

   * torchrun
   * deepspeed
   * accelerate
6. Expose high-level tools through MCP.
7. Provide a human CLI.
8. Persist node state, job state, logs, and audit events.
9. Start with allow-all mode.
10. Add Linux sandbox support later without API redesign.
11. Authenticate workers and clients before accepting control-plane messages.

### Security goals

1. Do not rely on the LLM to behave safely.
2. Do not expose raw unrestricted shell as the main interface.
3. Every operation must pass through a policy layer.
4. Every process launch must pass through a sandbox layer.
5. Worker-side policy is the final enforcement point.
6. The coordinator can do policy checks for UX, but workers must re-check locally.
7. Every operation should be auditable.
8. Secrets should be redacted from logs.
9. Bearer tokens should be read from files instead of command-line arguments.
10. Future sandboxing should restrict:

   * filesystem access
   * network access
   * device access
   * process lifetime
   * resource usage

### Non-goals for now

The first version does not need:

* macOS support
* Windows support
* Kubernetes integration
* Slurm integration
* full web UI
* multi-user permission isolation
* perfect untrusted-code security


## 5. Main Components

### 5.1 Coordinator

The coordinator is the central control plane.

Responsibilities:

* maintain node registry
* receive worker heartbeats
* expose CLI API
* expose MCP tools
* schedule jobs
* generate task specs
* aggregate logs
* persist job state
* write audit logs
* perform coordinator-side policy checks

The coordinator should not assume that its policy check is enough. Workers must still enforce local policy.

---

### 5.2 Worker

The worker is a daemon running on each Linux machine.

Responsibilities:

* connect to coordinator
* register node metadata
* send heartbeat
* receive task assignments
* enforce local policy
* prepare Linux sandbox
* start processes
* stream stdout/stderr
* kill process groups
* report exit status
* collect GPU/system info

Example startup:

```bash
agent-worker \
  --coordinator ws://10.0.0.1:8765 \
  --token-file ~/.agent-runtime/worker.token \
  --node-name gpu-node-01 \
  --workspace-root /mnt/workspace \
  --policy /etc/agent-runtime/policy.yaml
```

---

### 5.3 MCP Server

The MCP server exposes high-level tools to Codex / Claude / OpenCode.

It should expose structured tools like:

```text
cluster_status
list_nodes
gpu_status
run_process
start_job
tail_job
kill_job
dry_run_torchrun
launch_torchrun
collect_logs
collect_artifacts
check_policy
```

Avoid making raw shell the main abstraction.

Bad:

```text
run_shell(command)
```

Better:

```text
run_process(nodes, argv, cwd, env, sandbox_profile)
```

Best for common workflows:

```text
launch_torchrun(torchrun_spec)
```

---

### 5.4 CLI

The CLI is for humans and debugging.

Example:

```bash
agentctl nodes
agentctl gpu
agentctl run --nodes node-a,node-b -- hostname
agentctl job tail job_123
agentctl job kill job_123
```

Current job inspection commands:

```bash
agentctl job list
agentctl job tail job_123 --lines 100
agentctl job kill job_123
```

For training:

```bash
agentctl torchrun \
  --nodes node-a,node-b \
  --workspace /mnt/workspace/Wan-Trainer \
  --nproc-per-node 8 \
  -- python train.py --config configs/train.yaml
```

## 6. Core Execution Flow

Every process launch should follow this path:

```text
TaskSpec received by worker
  ↓
Convert to OperationRequest
  ↓
PolicyEngine.authorize()
  ↓
If deny: reject
  ↓
If ask: return approval-required
  ↓
Select SandboxProfile
  ↓
SandboxBackend.prepare()
  ↓
Executor.start()
  ↓
Stream logs
  ↓
Report status
```

Even in v0.1:

```text
PolicyEngine = AllowAllPolicy
SandboxBackend = NoneSandbox
```

The path should still be the same.

## 7. Core Data Structures

### 7.1 RunSpec

`RunSpec` is the canonical typed representation of a process launch.

```rust
pub struct RunSpec {
    pub job_id: JobId,
    pub task_id: TaskId,
    pub node_id: NodeId,

    pub argv: Vec<String>,
    pub cwd: PathBuf,
    pub env: BTreeMap<String, String>,

    pub timeout: Option<DurationSpec>,
    pub resources: ResourceSpec,
    pub filesystem: FilesystemSpec,
    pub network: NetworkSpec,
    pub devices: DeviceSpec,

    pub sandbox: SandboxRequest,
    pub secrets: Vec<SecretRef>,
    pub log_policy: LogPolicy,
}
```

Prefer this:

```json
{
  "argv": ["python", "train.py", "--config", "configs/train.yaml"]
}
```

Avoid this as the default:

```json
{
  "shell": "python train.py --config configs/train.yaml"
}
```

Shell execution can exist, but it should be treated as higher risk.

```rust
pub enum DecisionKind {

```

## 8. Policy Design

### 8.1 Policy modes

Support these modes eventually:

```text
allow_all
  Allow everything, but log every decision.

ask_dangerous
  Allow common workspace operations.
  Ask for high-risk actions.
  Deny known destructive actions.

deny_by_default
  Deny unless explicitly allowed.

readonly
  Allow inspection only.
  Deny process.start and filesystem.write.

workspace_write
  Allow writes only inside configured workspace.

training_full
  Allow GPU, NCCL, cluster networking, dataset reads, and output writes.
```

For v0.1, use:

```yaml
mode: allow_all
```

But still pass all operations through the policy engine.

---

### 8.2 Example policy file

```yaml
version: 1

mode: allow_all

workspaces:
  - id: wan-trainer
    path: /mnt/workspace/Wan-Trainer
    read: true
    write: true

nodes:
  - name: gpu-node-01
    labels: ["gpu", "a100"]
    allowed_workspaces: ["wan-trainer"]

rules:
  - name: deny-dangerous-system-ops
    effect: deny
    actions:
      - process.start
    command_patterns:
      - "rm -rf /"
      - "mkfs*"
      - "shutdown*"
      - "reboot*"
      - "mount*"
      - "chmod -R /"
      - "chown -R /"

  - name: allow-training-commands
    effect: allow
    actions:
      - process.start
      - process.tail
      - process.kill
    command_prefixes:
      - python
      - torchrun
      - accelerate
      - deepspeed
      - bash
    workspaces:
      - wan-trainer

  - name: ask-for-outside-workspace-write
    effect: ask
    actions:
      - filesystem.write
    paths:
      - "!/mnt/workspace/**"
```

In `allow_all` mode, deny rules may be disabled at first. But the schema should already support them.

## 9. Linux Sandbox Design

### 9.1 Sandbox backends

Only Linux is supported.

Backends:

```text
none
  No OS-level sandbox.
  Used for v0.1 and trusted development.

bubblewrap
  Main Linux sandbox backend.
  Used for filesystem and process containment.

landlock
  Optional future filesystem restriction layer.

docker
  Optional future container backend.

apptainer
  Optional future HPC-friendly container backend.
```

For the first serious sandbox implementation, use:

```text
bubblewrap
```

---

### 9.2 SandboxBackend trait

```rust
#[async_trait::async_trait]
pub trait SandboxBackend: Send + Sync {
    async fn prepare(
        &self,
        spec: &RunSpec,
        decision: &PolicyDecision,
    ) -> anyhow::Result<SandboxCommand>;

    async fn cleanup(
        &self,
        handle: &SandboxHandle,
    ) -> anyhow::Result<()>;
}
```

---

### 9.3 SandboxCommand

```rust
pub struct SandboxCommand {
    pub program: PathBuf,
    pub args: Vec<String>,
    pub cwd: PathBuf,
    pub env: BTreeMap<String, String>,
    pub kill_process_group: bool,
}
```

For `none`, this is almost the original command.

For `bubblewrap`, this becomes:

```text
program = bwrap
args = [
  "--ro-bind", "/", "/",
  "--bind", workspace, workspace,
  "--chdir", cwd,
  "--",
  original_program,
  original_args...
]
```

---

### 9.4 Sandbox profiles

#### `none`

```yaml
profile: none
backend: none
filesystem: unrestricted
network: allow
devices:
  gpu: true
  infiniband: true
```

Use for trusted development only.

---

#### `readonly-inspect`

For code inspection and log reading.

```yaml
profile: readonly-inspect
backend: bubblewrap

filesystem:
  read:
    - "{workspace}"
    - "/usr"
    - "/lib"
    - "/lib64"
    - "/bin"
  write:
    - "/tmp/agent-runtime/{job_id}"
  deny:
    - "{home}/.ssh"
    - "{home}/.aws"
    - "{home}/.config/gcloud"

network:
  mode: deny

devices:
  gpu: false
  infiniband: false
```

---

#### `workspace-write`

For normal coding-agent edits and tests.

```yaml
profile: workspace-write
backend: bubblewrap

filesystem:
  read:
    - "/"
  write:
    - "{workspace}"
    - "/tmp/agent-runtime/{job_id}"
  deny:
    - "{home}/.ssh"
    - "{home}/.aws"
    - "{home}/.config/gcloud"
    - "{workspace}/.env"

network:
  mode: deny

devices:
  gpu: false
  infiniband: false
```

---

#### `training-full`

For multi-node GPU training.

```yaml
profile: training-full
backend: bubblewrap

filesystem:
  read:
    - "/"
    - "/datasets"
  write:
    - "{workspace}"
    - "{workspace}/outputs"
    - "/tmp/agent-runtime/{job_id}"

network:
  mode: allowlist
  allow:
    - "cluster-subnet"
    - "master-addr"

devices:
  gpu: true
  infiniband: true
```

This profile should usually require user approval unless the policy explicitly allows it.

---

### 9.5 Bubblewrap command shape

A conceptual command:

```bash
bwrap \
  --die-with-parent \
  --new-session \
  --ro-bind / / \
  --bind /mnt/workspace/Wan-Trainer /mnt/workspace/Wan-Trainer \
  --bind /tmp/agent-runtime/job_001 /tmp/agent-runtime/job_001 \
  --proc /proc \
  --dev /dev \
  --chdir /mnt/workspace/Wan-Trainer \
  -- \
  python train.py --config configs/train.yaml
```

For `training-full`, GPU devices and Infiniband may need to be exposed.

For stricter profiles, device access should be reduced.

## 10. Executor Design

### 10.1 Executor trait

```rust
#[async_trait::async_trait]
pub trait Executor: Send + Sync {
    async fn start(&self, command: SandboxCommand) -> anyhow::Result<TaskHandle>;

    async fn kill(&self, task_id: &TaskId) -> anyhow::Result<()>;

    async fn tail(
        &self,
        task_id: &TaskId,
        lines: usize,
    ) -> anyhow::Result<Vec<LogLine>>;

    async fn status(&self, task_id: &TaskId) -> anyhow::Result<TaskStatus>;
}
```

### 10.2 Requirements

The executor should:

* use `tokio::process::Command`
* avoid shell by default
* support shell explicitly when requested
* create a process group
* kill the whole process group on cancellation
* capture stdout and stderr separately
* stream logs to coordinator
* write logs to local disk
* preserve exit code
* support timeout
* eventually support PTY

## 11. Worker RPC

### 11.1 Transport

Use this for v0.1:

```text
WebSocket + JSON
```

Later:

```text
gRPC streaming
```

The worker connects to coordinator.

### 11.2 Message types

```rust
pub enum WorkerMessage {
    Register(NodeInfo),
    Heartbeat(NodeHeartbeat),
    TaskStarted(TaskStarted),
    LogLine(LogLine),
    TaskExited(TaskExited),
    Error(WorkerError),
}

pub enum CoordinatorMessage {
    StartTask(TaskSpec),
    KillTask(TaskId),
    TailTask(TaskId),
    Ping,
    UpdatePolicy(PolicyConfig),
}
```

### 11.3 Reconnect behavior

Worker should:

* reconnect with exponential backoff
* keep local task state on disk
* continue running existing tasks unless told otherwise
* report current task state after reconnect

Coordinator should:

* mark node offline after missed heartbeats
* mark node online again after reconnect
* resync running jobs from worker

## 12. Job Model

### 12.1 Job

A job is a user-visible unit of work.

Examples:

```text
single command
multi-node command fanout
torchrun job
deepspeed job
distributed evaluation
```

### 12.2 Task

A task is a concrete process on one worker.

One job may have many tasks.

Example:

```text
job_001
  task_001 on node-a
  task_002 on node-b
```

### 12.3 Failure policy

For distributed jobs, default should be:

```text
if one task fails, kill all tasks in the same job
```

Example:

```yaml
failure_policy:
  kill_all_on_failure: true
  collect_logs: true
  collect_artifacts: true
  max_restarts: 0
```

## 13. Multi-Node Training

### 13.1 Torchrun

The coordinator should generate per-node commands.

For two nodes:

Node 0:

```bash
torchrun \
  --nnodes=2 \
  --nproc-per-node=8 \
  --node-rank=0 \
  --master-addr=10.0.0.1 \
  --master-port=29500 \
  train.py --config configs/train.yaml
```

Node 1:

```bash
torchrun \
  --nnodes=2 \
  --nproc-per-node=8 \
  --node-rank=1 \
  --master-addr=10.0.0.1 \
  --master-port=29500 \
  train.py --config configs/train.yaml
```

### 13.2 TorchrunSpec

```rust
pub struct TorchrunSpec {
    pub nodes: Vec<NodeSelector>,
    pub workspace: PathBuf,
    pub entrypoint: Vec<String>,
    pub args: Vec<String>,
    pub nproc_per_node: usize,

    pub master_addr: Option<String>,
    pub master_port: Option<u16>,

    pub env: BTreeMap<String, String>,
    pub sandbox_profile: String,
}
```

### 13.3 Coordinator responsibilities

Before launch:

```text
1. Check all nodes online.
2. Check GPU availability.
3. Check workspace exists on all nodes.
4. Check git commit consistency.
5. Choose master node.
6. Choose master address.
7. Choose master port.
8. Assign node ranks.
9. Generate one RunSpec per node.
10. Dry-run the commands.
11. Ask for approval if required.
12. Start all tasks.
13. Stream logs.
14. Kill all tasks if one fails.
```

## 16. Authentication

### v0.1

Token-based authentication.

Coordinator:

```bash
agent-coordinator \
  --worker-token-file ~/.agent-runtime/worker.token \
  --client-token-file ~/.agent-runtime/client.token
```

Worker:

```bash
agent-worker --token-file ~/.agent-runtime/worker.token
```

Client:

```bash
agentctl --token-file ~/.agent-runtime/client.token nodes
```

The coordinator validates `Authorization: Bearer <token>` during the WebSocket
upgrade handshake. Connections also identify their role with `X-Agent-Role` so
worker and client tokens can be separated.

### Future

Add mTLS.

For now, keep it simple:

```text
bearer tokens from local files
trusted private network
worker only connects to configured coordinator
```

### tmux supervisor

For lab usage before systemd packaging, use:

```bash
scripts/agent-runtime-tmux.sh start-master
scripts/agent-runtime-tmux.sh start-worker
scripts/agent-runtime-tmux.sh status
scripts/agent-runtime-tmux.sh stop
```

The script starts coordinator and worker processes inside tmux windows, writes
logs under `~/.agent-runtime`, and uses token files rather than command-line
passwords.

## 17. Secrets

Do not send raw secrets in normal job specs.

Use secret references:

```json
{
  "secrets": ["WANDB_API_KEY", "HF_TOKEN"]
}
```

Worker resolves them locally.

Rules:

```text
1. Never return secret values to MCP clients.
2. Never store secrets in plaintext job specs.
3. Inject secrets into process env only when needed.
4. Redact secrets from logs.
5. Redact secrets from audit events.
```

## 21. Final Simplified Design

The simplified Linux-only architecture is:

```text
Codex / Claude / OpenCode
        ↓
MCP server / CLI
        ↓
Coordinator
        ↓
Linux worker daemon
        ↓
PolicyEngine
        ↓
Linux SandboxBackend
        ↓
Executor
        ↓
Process
```

For v0.1:

```text
PolicyEngine = allow_all
Linux SandboxBackend = none
```

For future sandboxed releases:

```text
PolicyEngine = allow / ask / deny
Linux SandboxBackend = bubblewrap
```

The important design rule is:

> Even when sandbox is disabled, the runtime should behave as if sandbox exists.
> The abstraction should be present from day one.
